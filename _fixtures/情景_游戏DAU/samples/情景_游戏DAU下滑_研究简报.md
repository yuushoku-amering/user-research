# 情景研究简报 · 网游 A 2.2 版本 DAU 下滑

> **情景**（研究员口述）：长线运营网游 A，2.1 版本平均日活 2w；2.2 版本更新仅 1 周，日活掉到 7k。要求分析原因。
> 类型：**假设情景（练习）**；产物格式与真实项目一致。
> 产出者：组块 0（研究设计 & 主题澄清）。

---

## 0. 必须先澄清（模型提出的疑问）
⚠️ 下面几条不解决，后面所有分析都可能白做：

1. **口径一致性**
   - "2.1 平均日活 2w"是**哪个口径、哪个时间窗**（整月日均？含活动峰值？）
   - "7k"是**日均**、**某一天**、还是**某一渠道**？
   - 需核对：DAU 定义（登录去重 / 完成某行为）、去重规则、统计时区、**2.2 是否改过埋点**
2. **"掉"的形状**：是 2.2 上线**当天骤降**，还是**一周内渐进下滑**？
   - 骤降 → 更像**事故 / 口碑事件 / 外部冲击**
   - 渐进 → 更像**内容消耗 / 流失累积**
   - 需要**日粒度曲线**：更新前 4 周 + 更新后 1 周
3. **DAU 结构拆解**（DAU = 新增 + 老用户 + 回流）
   - 新增断崖（买量/渠道/商店推荐位）→ **市场问题，不是版本问题**
   - 老用户流失（内容/经济系统/技术）→ 版本相关
   - 回流减少（活动结束自然回落）
4. **同期的外部与运营变动**（至少排除一遍）：买量预算、版本活动/联动、开服合服、服务器事故、竞品大版本、假期/考试周、渠道政策
5. **"流失" vs "波动"**：需要 **2.1 版本内的日活基线**做参照，否则分不清"掉"和"回基线"

---

## 1. 背景与业务问题
2.2 更新后一周，DAU 由 2.1 的 2w 降至 7k（约 -65%）。业务侧需要判断：**是不是版本内容出了问题、要不要补救、补救什么。**

## 2. 研究目的
**定位 DAU 下滑的主因成分，并给出可行动的补救方向**（继续观察 / 热修 / 补偿召回 / 内容调整 / 回滚评估）。
- 决策用途：决定 2.2 的处置与后续运营资源投向

## 3. 研究问题（RQ）
- **RQ1 结构**：下滑集中在哪些人群/渠道/平台/服务器？新老回流如何拆分？留存曲线怎么变？
- **RQ2 时间形态**：下滑的时间点与 2.2 内容上线节奏、外部事件是什么关系？
- **RQ3 动机**：流失玩家为什么走？为什么不再回来？
- **RQ4 归因权重**：版本内容 / 技术体验 / 经济系统 / 社交 / 竞品 / 外因，各贡献多少？
- **RQ5 保护因素（反向）**：留下的玩家为什么不走？（可复用的留存抓手）

## 4. 假设（待验证，**不是结论**）
- **H1** 技术体验问题（卡顿/闪退/回档/排队）直接导致部分玩家流失
- **H2** 2.2 经济/数值改动伤害老玩家的"投入感"（感知受损 → 离开）
- **H3** 新增下滑（买量/渠道）是 DAU 跌幅的主要成分之一 ← **必须优先排除**
- **H4** 社交关系链断裂（好友流失）放大流失

## 5. 目标人群与抽样
- **量化**：全量行为数据（2.1 前 4 周 ~ 2.2 后 1 周）
- **质性**：**流失玩家**（2.1 活跃 + 2.2 后 7 日未登录）12~20 人；**留存玩家** 6~10 人作对照
- 招募渠道：游戏内邮件/弹窗、官方社群、客服回访、召回短信
- ⚠️ **幸存者偏差**：只在游戏内招募，招到的都是"还在游戏里的人" → 必须**走出游戏**（社群/短信/第三方社区）

## 6. 关键变量与操作化定义
| 变量 | 角色 | 操作化 | 测量层次 | 来源 |
|---|---|---|---|---|
| 是否流失 | 因变量 | 2.2 后 7/14 日未登录（0/1）；活跃天数变化 | 定类 / 定距 | 行为数据 |
| 技术体验问题 | 自变量 | 闪退/卡顿/排队/回档 是否遇到 + 频次 | 定类 / 定距 | 日志 + 问卷 |
| 版本内容满意度 | 自变量 | 新内容/新玩法满意度量表（3~5 题） | 定距 | 问卷 |
| 经济系统感知 | 自变量 | 数值改动公平性、氪金压力（3 题） | 定距 | 问卷 |
| 社交粘性 | 中介/调节 | 好友数、是否有固定队、公会活跃度 | 定距 / 定类 | 行为 + 问卷 |
| 竞品吸引 | 自变量 | 同期是否在玩竞品大版本 | 定类 | 问卷 |
| 外因 | 控制 | 学期阶段、设备性能、可支配时间 | 定类 | 问卷 |
| 用户类型 / 付费层级 | 控制 | 新/老/回流；0 / 小R / 中R / 大R | 定类 / 定序 | 行为数据 |

## 7. 数据条件（研究员补充确认）
- ✅ **只有后台监测数据**（日志 / 埋点），DAU 统一按"平均日活"口径
- ❌ **没有任何线上/线下访谈，也没有问卷**
- ⚠️ 这决定了路径：**不是"直接去访谈"，而是「先让数据说话 → 再决定问什么」**

## 8. 分析思路：**分两阶段**
### 阶段 A · 现有后台数据（零成本，立刻可做）
见 `情景_游戏DAU下滑_阶段A后台数据分析方案.md`
→ 产出：**候选假设 + 每条假设的数据支持 / 反驳**（是假设，不是结论）

### 阶段 B · 由阶段 A 的发现决定要不要补充收集
| 阶段 A 的发现 | 下一步 |
|---|---|
| 技术指标异常（崩溃 / 排队 / 延迟 ↑） | 可直接定位，**未必需要访谈** |
| 老用户流失 + 核心玩法参与率 ↓ | 访谈 + 问卷（问动机） |
| 新增断崖 / 渠道变化 | 查**买量、渠道、商店推荐位**（市场问题，非版本问题） |
| 数据说不清 | 先扒**现成质性数据**：舆情（TapTap/贴吧/NGA/B站/官群）+ **客服工单** |
| 任何情况 | **内部访谈**（策划/运营/客服/数据）→ "2.2 改动清单 + 同期运营动作清单"（最快最省，不用招募审批） |

## 9. 约束与伦理
- 数据窗口仅 1 周 → 结论用"倾向性"表述，别下死结论
- 内部数据敏感 → 报告**去标识化**（用户 ID 哈希，不出现可识别信息）
- 流失玩家触达难且要合规 → 联系频次与话术需运营审核
