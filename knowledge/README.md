# 知识库 · 索引

这个目录里的东西不是代码，是**规则**——工作台判断"这样写行不行"的依据。
它们和 `engine.py` 分开放，原因很直接：**规则应该能被研究员看见、改掉、追问出处**，
而不是埋在 Python 里只有作者知道。

## 文件格式

每个 `.md` 文件里有：

1. 人读的解释（这份规则在说什么、为什么）
2. 一段 ` ```json ` 机器读的 `rules`（引擎照着它判）
3. **出处**（provenance）——这条从哪来、属于哪一类

## 出处标记：惯例还是某家观点

每条规则都带 `source` 和 `kind` 两个字段：

- `kind: "convention"` —— **行业惯例**。产品研究/用户研究领域普遍这么做，
  多份公开方法论一致。可以当作"通行做法"引用。
- `kind: "opinion"` —— **某一家或某一派的做法**。有道理，但不是共识，
  换个流派/换种范式就会有不同的选择。
- `kind: "heuristic"` —— **经验法则**。实用、被广泛采用，但缺少严格证据支持，
  数字是经验值而不是推导值。

**为什么非要分这个**：学术场景里，答辩会被问"你凭什么这么做"。
"这是通行做法"和"这是某公司的偏好"是两个完全不同的回答。
工作台把标记摆在明面上，是为了让你**能分清、也能改**——不认同哪条，直接改文件。

## 目前的外部参考

第一批规则（研究问题动词、样本量、按人群分别计算）参考了
[Cookiy AI 的用户研究 skill](https://github.com/cookiy-ai/user-research-skill)（MIT 协议）
里的 `qualitative-research-planner`。
我们吸收的是它的**规则骨架**，没有搬它的文字，也没有采用它"让模型读完 50 份转写稿
自己出结论"的做法——工作台的立场是判断留在研究员手里。

原始参考文件留了一份在 `workbench/_ref/`，方便对照。
